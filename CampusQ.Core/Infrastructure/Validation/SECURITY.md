# CampusQ Security & Validation Guide

## Input Validation

All user inputs are validated before database operations using the `QueueInputValidator` class.

### Validated Inputs:
- **Purpose**: Max 200 characters, cannot be empty
- **Service**: Must be one of: Admission, Cashier, Registrar
- **TicketNumber**: Must be positive integer

### Example Usage:

```csharp
using CampusQ.Core.Infrastructure.Validation;

// Validate a queue entry
try
{
	QueueInputValidator.ValidateQueueEntry(entry.Purpose, entry.Service);
	// Validation passed, proceed with database operation
}
catch (ArgumentException ex)
{
	// Handle validation error
	Console.WriteLine($"Validation failed: {ex.Message}");
}
```

## SQL Injection Prevention

All database queries use **parameterized queries** (SqlParameter) to prevent SQL injection attacks.

### ✓ SAFE - Parameterized Query:
```csharp
cmd.CommandText = "SELECT * FROM dbo.Queue WHERE Service = @service";
cmd.Parameters.AddWithValue("@service", userInput);
```

### ✗ UNSAFE - String Concatenation (DO NOT USE):
```csharp
// NEVER DO THIS - vulnerable to SQL injection!
cmd.CommandText = $"SELECT * FROM dbo.Queue WHERE Service = '{userInput}'";
```

## Custom Exceptions

Two custom exceptions for better error handling:

### ValidationException
Thrown when input validation fails:
```csharp
try
{
	QueueInputValidator.ValidateQueueEntry(purpose, service);
}
catch (ArgumentException ex)
{
	throw new ValidationException($"Invalid queue entry: {ex.Message}");
}
```

### RepositoryException
Thrown when database operations fail:
```csharp
catch (SqlException ex)
{
	throw new RepositoryException("Failed to add queue entry", ex);
}
```

## Security Best Practices

### ✓ DO:
- ✅ Validate all user inputs before database operations
- ✅ Use parameterized queries exclusively
- ✅ Handle exceptions gracefully without exposing sensitive details
- ✅ Use environment variables for sensitive configuration
- ✅ Enable SQL Server encryption (Encrypt=True)
- ✅ Use integrated security where possible
- ✅ Log security events and errors
- ✅ Use HTTPS for all web communications

### ✗ DON'T:
- ❌ Concatenate user input into SQL queries
- ❌ Store hardcoded secrets in source code
- ❌ Ignore validation errors silently
- ❌ Expose database error details to users
- ❌ Use weak passwords or shared credentials
- ❌ Trust user input without validation
- ❌ Log sensitive information (passwords, PII)

## Data Validation Rules

### Service Names (Enum-like)
Allowed values: `Admission`, `Cashier`, `Registrar`

Only these three services can be stored. Any other value is rejected.

### Purpose
- Non-nullable
- Max 200 characters
- Any characters allowed
- Not treated as a command or identifier

### Ticket Numbers
- Must be positive (> 0)
- Must be within Int32 range
- Automatically generated by database (IDENTITY)

## Audit and Logging

All database operations are logged with:
- Operation type (Add, GetAll, GetByTicketNumber, etc.)
- Parameters (service name, ticket number)
- Timestamp
- Errors/exceptions

Log output goes to:
- Console (development)
- Debug output (debugging)
- Event Log (production/Windows services)

## Testing Validation

To test validation before production deployment:

```csharp
var validator = QueueInputValidator;

// Test empty service - should throw
try
{
	validator.ValidateServiceName("");
	// Should not reach here
}
catch (ArgumentException ex)
{
	Console.WriteLine($"Caught expected error: {ex.Message}");
}

// Test invalid service - should throw
try
{
	validator.ValidateServiceName("InvalidService");
	// Should not reach here
}
catch (ArgumentException ex)
{
	Console.WriteLine($"Caught expected error: {ex.Message}");
}

// Test valid ticket number - should pass
validator.ValidateTicketNumber(12345);
Console.WriteLine("Ticket number validation passed");
```

## OWASP Top 10 Mitigation

This application addresses the following OWASP risks:

1. **Injection (SQL Injection)** - Mitigated by parameterized queries
2. **Broken Authentication** - Secured via Windows Auth + future OAuth
3. **Sensitive Data Exposure** - Connection strings in env vars, https enabled
4. **Input Validation** - All inputs validated before processing
5. **Error Handling** - Structured exception handling, no sensitive details in responses
